## 3. Устройство HTTP-клиента и предметного API

src/api-client.js — общий транспорт, не знает о задачах. Экспортирует ApiError, buildUrl и createApiClient. Метод requestJson(path, { method, query, body, signal, timeoutMs }):

- допускает только GET, POST, PATCH, DELETE; метод нормализуется в верхний регистр;
- запрещает тело у GET до сетевого запроса;
- добавляет Accept: application/json к каждому запросу;
- при наличии тела выполняет JSON.stringify и добавляет Content-Type: application/json;
- объединяет внешний AbortSignal и AbortSignal.timeout через AbortSignal.any;
- различает отказ fetch (network, timeout, aborted) и обработку полученного Response;
- сначала проверяет response.ok, затем Content-Type, затем разбирает JSON;
- для 204 возвращает null до чтения тела;
- HTTP-ошибка сохраняет status, code, details, url; сообщение сервера сохраняется, но проверки строятся по коду.

src/task-api.js — предметный слой, не работает с DOM. Экспортирует createTaskApi(client) с методами:

| Метод | Результат |
|---|---|
| getTasks(filters, options) | { tasks, meta } |
| getTaskById(id, options) | задача |
| getCategories(options) | массив категорий |
| createTask(draft, options) | созданная задача |
| updateTask(id, changes, options) | обновлённая задача |
| setTaskCompleted(id, completed, options) | обновлённая задача |
| deleteTask(id, options) | null |
| resetDemoData(options) | { reset: true, total } |
| loadInitialData(filters, options) | { tasks, categories, meta } |

Фильтры нормализуются до запроса; допускаются только completed, priority, categoryId, q. После запроса проверяется схема задачи и категории, уникальность id и meta.total === data.length. Неверная схема — ApiError с kind: "invalid-response". loadInitialData запускает getTasks и getCategories до общего await через Promise.all.

## 4. Схема асинхронных состояний

| Состояние | Значение | Представление |
|---|---|---|
| loading | ответ ещё не получен | сообщение «Загрузка…», aria-busy="true" |
| ready | получен непустой список | карточки и число найденных |
| empty | запрос успешен, результатов нет | явное сообщение без старых карточек |
| error | запрос завершился ошибкой | сообщение и кнопка повтора |

Изменяющая операция дополнительно блокирует кнопки через setMutationPending(true/false). empty не считается ошибкой.

## 5. Защита от устаревшего ответа

src/app-controller.js хранит activeController и requestSequence. При новой загрузке:

1. requestSequence увеличивается;
2. предыдущий AbortController вызывается abort();
3. создаётся новый AbortController, его сигнал передаётся в API;
4. результат применяется только если sequence === requestSequence.

Отмена (kind: "aborted") не показывается пользователю как ошибка. Проверка номера нужна даже при отмене, потому что источник может завершить операцию, не отреагировав на сигнал немедленно.

## 9. Ответы на контрольные вопросы

**Почему после изменяющей операции выполняется повторный GET, а не локальное обновление массива?** Сервер — единственный источник истины. Повторный GET с текущими фильтрами показывает ровно то состояние, которое подтвердил сервер, включая назначенные id, начальный completed и порядок.

**Зачем нужна проверка номера запроса, если предыдущий запрос уже отменён?** AbortController — сигнал, но не гарантия, что источник немедленно прервёт операцию. Кэш, тестовый двойник или другая реализация могут завершить запрос, не отреагировав на сигнал. Проверка sequence === requestSequence отбрасывает устаревший результат независимо от того, отменился ли запрос.

**Чем empty отличается от error?** empty — успешный ответ с пустым результатом: это нормальный исход фильтра или пустого набора. error — запрос не завершился успехом. Пользователю показываются разные сообщения, и в error доступна кнопка повтора.

**Почему отмена не показывается как ошибка?** Отмена — ожидаемое управление потоком при смене фильтра, а не сбой. Показ сообщения при каждом переключении фильтра раздражал бы пользователя и скрывал реальные ошибки.

**Почему DELETE не разбирает JSON?** Сервер возвращает 204 без тела. Вызов response.json() на пустом теле приводит к ошибке разбора. Клиент возвращает null до проверки Content-Type.

**Почему HTTP-ошибка не маскируется сетевой?** Вызов fetchFn и обработка полученного Response разделены. Отказ fetch классифицируется как network/timeout/aborted, а не-2xx Response — как http. Широкий catch вокруг всего запроса превратил бы 404 в network и потерял бы статус.

**Почему false не заменяется строкой "false" до URLSearchParams?** buildUrl пропускает только undefined, null, "". Логическое false — содержательное значение и передаётся как есть, а строковое представление создаёт URLSearchParams. В предметном коде фильтр completed проверяется как boolean, а не как строка.

**Почему название выводится через textContent, а не innerHTML?** Название приходит с сервера и считается недоверенным. textContent выводит строку буквально; innerHTML интерпретировал бы её как разметку и позволил бы внедрить HTML.
