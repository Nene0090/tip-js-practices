## 5. Способы проверки id, повторений и значения false

- **id**: `parsePositiveId(raw)` сначала проверяет всю строку регуляркой `/^[1-9]\d*$/`, затем `Number.isSafeInteger`. `4abc`, `01`, `1e2`, `9007199254740992` — отклоняются (`null`). Одного `parseInt` недостаточно: он принял бы `4abc` как `4`.
- **Повторения**: `searchParams.getAll(name)` возвращает массив всех значений. Если длина > 1 — `ApiError(400, 'INVALID_QUERY')`. Превращать параметры в обычный объект до этой проверки нельзя: дубликаты потеряются.
- **false**: значения `completed` сравниваются строго со строками `'true'` и `'false'`, а результат — `boolean`. `completed=0`, `completed=False`, `completed=` отклоняются. В `selectTasks` условие `completed !== null` (не `if (filters.completed)`), иначе `false` отфильтровалось бы.

## 8. Обнаруженный и исправленный дефект

При первой реализации `selectTasks` фильтр `completed` применялся через `if (filters.completed) { ... }`. Из-за этого запрос `?completed=false` возвращал **выполненные** задачи: `false` в условии трактуется как «фильтр не задан». Дефект обнаружен тестом `Выборка completed=false`. Исправление: `if (completed !== null && task.completed !== completed) return false;` — отдельное сравнение и явная проверка на `null`, который обозначает отсутствие ограничения. После исправления все тесты `selectTasks` проходят.

## 9. Ответы на контрольные вопросы

**Почему в маршрутах используется `store`, а не прямой импорт `data.js`?** `store` — точка доступа к данным конкретного приложения. В тестах можно подставить свой `store` (например, с `listTasks`, выбрасывающим исключение, — для проверки 500 без утечки). Прямой импорт `data.js` в маршрутах сделал бы такую подстановку невозможной и нарушил бы разделение ответственности.

**Почему `meta.total` — размер выборки, а не хранилища?** Контракт ПР9: без фильтров `total = 12`, с фильтром `?categoryId=2` — `total = 6`. Это количество записей в ответе. Размер хранилища не нужен клиенту и не должен смешиваться с длиной `data`.

**Почему пустой результат фильтра — 200, а не 404?** Список задач — существующий ресурс. Отсутствие совпадений — нормальный исход фильтра. 404 зарезервирован для отсутствующей конкретной записи (`/tasks/:id`) и для неизвестного маршрута.

**Зачем проверять `getAll(name)` до преобразования в объект?** Превращение в объект (`Object.fromEntries`) оставит только последнее значение повторяющегося параметра, и проверка на дубликат станет невозможной. `getAll` возвращает все значения, что позволяет отклонить повторение с `400 INVALID_QUERY`.

**Почему `q` обрезается до проверки длины?** Контракт: «строка после trim, не длиннее 100 единиц». Пробелы по краям не считаются содержательной частью запроса. `q=' ' + 'я'.repeat(100) + ' '` валиден.

**Почему после `res.json` нужно завершать ветвь через `return`?** После отправки ответа повторная отправка вызовет ошибку `Cannot set headers after they are sent`. В обработчиках с ветвлением удобно использовать `return res.json(...)`.

**Почему 405 отдаётся даже для `DELETE /api/tasks/999`?** Контракт ПР9: у известных путей разрешены только GET, HEAD, OPTIONS. Проверка существования задачи для запрещённого метода не выполняется — сначала должен сработать 405, иначе можно случайно утечь информацию о существовании записи.

**Почему обработчик ошибок подключён последним?** Express вызывает middleware в порядке регистрации. Если `errorHandler` подключить раньше Router, ошибки из маршрутов до него не дойдут. Также `404 ROUTE_NOT_FOUND` регистрируется после Router, иначе он перехватит все запросы до маршрутов.
